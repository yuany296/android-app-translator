# ML Kit 覆盖层几何修复计划

- 日期：2026-09-29
- 触发：用户反馈「倾斜文本还是没有完全覆盖住，连角度和宽度都不对。还有它的字体大小和位置好像不对。
  对于 ML kit 的覆盖层位置处理我觉得还需要进行修复」。
- 适用范围：内嵌浏览器 DOM 覆盖层链路（`WebtoonImageTranslator.buildScene` →
  `BrowserSceneBuilder` → `assets/mt-overlay-renderer.js`）。

---

## 0. 一句话结论

PaddleOCR 走的是「检测网络 → 文字四边形」这条正路；**ML Kit 只给轴对齐的块级框**，
整条覆盖层链路的几何输入质量因此降了一档。目前的做法是「拿 ML Kit 的框当 PaddleOCR 的框用」，
再补一些启发式（墨迹收紧、最小面积外接矩形）去打补丁。要真正对齐参考插件的效果，
需要把「**几何来源**」这件事显式化：ML Kit 路径必须自己重建几何，而不是复用四边形路径的假设。

---

## 1. 现状与差距（已实测数据）

测试页 `.verify/web/dump.html`（`syn1.png` 内含 20° 斜排韩文 + 粉色旁白 + 日文竖排 + 白色实底），
`MTDUMP` 是页面回读真实 DOM 得到的几何。

### 1.1 已完成的部分

| 项 | 之前（ML Kit） | 现在 |
|---|---|---|
| 斜排倾角 | `rotate(0.00deg)`（完全没有） | `rotate(13.04deg)`（PaddleOCR 真实四边形给 11.30°，差 1.7°） |
| 斜排遮罩形状 | 轴对齐矩形 | 最小面积外接矩形顶点 → 真正的倾斜 `polygon(...)` |
| 斜排实底填充块 | `315.69 × 314.23` | `105.24 × 72.45` |
| 实底填充范围 | `fillW = 351% / 505%` | `fillW ≤ 120.7%`（限幅 1.4×） |
| 粉色旁白框 | `39.97 × 4.13` | `37.55 × 3.21`（墨迹收紧） |
| 彩色字 | 全被压成 `#181818` | `#e2467e` / `#163e6e` / `#1a1a2e`（与原图一致） |

### 1.2 仍然不对的部分（用户第 4 点的核心）

实测 `b0`（斜排气泡）当前值：

```
b0:cover  L38.83 T71.17  23.31 × 11.00   clip=polygon(15.51% 0%, 100% 41.57%, 84.53% 100%, 0% 58.52%)
b0:text   L38.83 T71.17  20.33 ×  6.64   rotate(13.04deg)   font=16.6px
```

问题清单：

| # | 现象 | 现状 | 根因 |
|---|---|---|---|
| A | **宽度不对** | 排版/遮罩框仍是 ML Kit 的块框（`20.33 × 6.64`），只有多边形换成了外接矩形 | `tightenRectToInk` 的「面积 < 92% 才替换」闸门太保守，面积只缩 5% 就不换 |
| B | **角度只能算「够用」** | 13.04° vs 真值 20°（像素空间）| 倾角是在**裁剪区域内**估的；区域内只剩字形时可用像素少，且字的笔画粗细会参与主轴 |
| C | **字号偏小** | `font=16.6px`，而框高 `6.64% × 1400px = 93px` 只放一行 | `originalLineHeightPx` 用「框高 ÷ 行数」，块框偏高时反而变大；收紧后框高又偏小 → 字号在两个错误值之间跳 |
| D | **位置偏移** | 文字节点按框中心 `translate(-50%,-50%)` 摆 | 外接矩形的 AABB 中心 ≠ 字形视觉中心（斜排时 AABB 的空白偏向一侧） |
| E | **覆盖不完全** | 遮罩 = 外接矩形 × 1.03 | 倾角估偏（B）时，外接矩形跟着偏 → 一侧露出笔画 |
| F | **seam 两个覆盖框** | A 图与 B 图各一个遮罩框，尺寸不同（`11.00` vs `8.62`） | 跨图那一半的遮罩用的是 `patch_box`（贴片区域），另一半用文字框，两者不是同一个框 |

## 2. 修复计划

分四步，按「收益 / 风险」排序。每步都可独立验证，不需要一次做完。

### 第 1 步：把「几何来源」显式化（结构性，先做）

**目的**：ML Kit 路径不再假装自己有四边形。

- `Bubble` 增加 `geometrySource: Quad | AxialBlock`（或等价的布尔 `hasQuad`，已有 `polygon != null` 可复用）。
- `buildScene` 按来源分两条分支，而不是「一条路径 + 兜底」：
  - `Quad`（PaddleOCR）：完全保持现状，**不动**（现在效果是对的）。
  - `AxialBlock`（ML Kit）：走新的 `MlKitGeometryResolver`，产出
    `(排版框, 遮罩四边形, 填充框)` 三元组。
- 好处：后续所有 ML Kit 的启发式都集中在一个类里，不会污染 PaddleOCR 的路径；
  也便于回归对比（同一张图切引擎跑两遍）。

**验收**：切 PaddleOCR 时 `MTDUMP` 与改动前逐字节一致。

---

### 第 2 步：修 A/B/C/D（ML Kit 几何重建）

#### 2.1 排版框直接取「最小面积外接矩形」的 AABB，不再用 ML Kit 的块框

现在只在面积缩小 > 8% 时才替换。改为：**只要外接矩形可用就替换**，并去掉 92% 闸门
（闸门当初是为了「避免几像素抖动改布局」，但 A/C/D 三个问题都是它导致的）。

- 影响：字号按真实字高重算（修 C），文字中心按真实字形中心（修 D）。
- 风险：外接矩形偶尔会被杂线干扰 → 保留 `MIN_ANISOTROPY ≥ 2.0` 与 `MAX_ABS_DEG = 45°` 两道闸，
  并且**只在横排气泡**上做（竖排跳过，已有）。

#### 2.2 倾角估计改为「逐行估计 + 取中位数」

现在的 13.04° 是整块墨迹一个外接矩形。参考 PP-OCR 的做法是按**文本行**估角：

1. 把墨迹按 y 投影切成行带（相邻行之间找空白谷）；
2. 每行单独求最小面积外接矩形 → 一个角度样本；
3. 取样本中位数（抗离群），行数 < 2 时退回整块估计。

**验收**：`TextTiltEstimatorTest` 增加「多行不同长度/不同间距」用例；
设备上 `syn1.png` 的斜排气泡应从 13.04° 靠近 20°（像素空间）。

#### 2.3 用外接矩形的顶点反推排版框（而不是 AABB）

斜排时 AABB 会包含大量空白。做法：

- 遮罩四边形 = 外接矩形顶点（已实现）；
- 排版框 = 外接矩形的**内接轴对齐框**（沿长边取 `longSide × cosθ` 宽度），
  保证译文基线落在字形带内；
- 文字节点仍按框中心摆，但因为框贴住了字形，中心自然对齐（修 D）。

#### 2.4 字号：先按原文，放不下才缩，且缩到「框内」为止

用户第 2 点：**「字体大小虽然要仿照原文。但是当文字太多的时候，文字可以适量缩小，以至于适应 OCR 到的框大小。」**

现状：`resolveFontSizeRange` 的 `maxFont = min(120, 框高×0.88, 原字高×1.08)`，
`fitBubbleFontSize` 用离屏探针二分——**逻辑本身是对的**，但两个输入坏了：

- `fixed_font_percent`（跨图气泡）会**完全跳过拟合**，于是跨页那一半永远不缩（见第 3 步）；
- 框高来自被污染/被收紧的框 → `originalH` 不准。

要做：
1. 拟合的**起点**继续用原文字高（`startSize = originalH`），符合「仿照原文」；
2. 拟合的**上限**放宽到框高（`maxFont = 框高 × 0.98`），不再被 `原字高 × 1.08` 卡死 —— 字少时能放大到框内；
3. 文字过多时**允许缩到 `MIN_FONT`（10px）**，并保证不溢出框（二分本来就保证）；
4. 增加一条「装不下就缩，缩到极限仍溢出才撑框」的显式顺序（现在是先缩后撑，保持）。
5. 去掉跨图气泡的 `fixed_font_percent` 短路：改为「用上一张图算出的字号作为**起点**」，
   仍允许本图按自己的框微调（避免接缝两侧一个被缩、一个不缩）。

**验收**：`mt-overlay-acceptance.test.js` 增加「长译文缩到框内、短译文放到框内、原字高可信时不设 52px 硬顶」；
设备上用一张「短句气泡 + 长句气泡」的对照页核对。

---

### 第 3 步：seam 只保留一个覆盖框（用户第 1 点）

现状：跨图气泡在 A 图用**文字框**做遮罩，在 B 图用 **`patch_box`（贴片区域）** 做遮罩，
两个框尺寸不同（实测 `11.00` vs `8.62`）→ 视觉上像两个框。

方案：**遮罩只用「共享文字框」，贴片只是它的背景。**

- `CrossBubblePart` 已经带了 `sourceBoxPercent`（上一张图算好的百分比框）；
- 让 B 图的跨图气泡**用同一个框**当遮罩（现在用于文字），贴片继续按 `patch_box` 画在遮罩内部；
- 即：遮罩框 = `sourceBoxPercent` 换算值（两图完全一致），`patch_box` 退化为「背景贴图的目标区域」，
  不再决定遮罩边界。

**验收**：`seamdump.html` 里 A/B 两半的 `b0:cover` / `c0:cover` 的
`left/top/w/h` 必须逐字段一致（只有 y 相差一整张图的高度）。

---

### 第 4 步：粉字没有清理图（用户第 3 点）

**先排除的**：清理图缓存**不是**原因。`CleanedImageProcessor.cacheKey` 已经区分模式：

```kotlin
private fun cacheKey(pageHash: String, includeSolid: Boolean): String =
    if (includeSolid) "$pageHash|include_solid" else pageHash
```

所以「开/关精细擦字」不会互相复用。用户怀疑的「缓存互通」不成立，需要换方向查。

**当前实测**：粉色旁白的遮罩节点**确实挂上了清理图 URL**
（`bgImg: url("https://mtlocal.overlay/c15812285733700.jpg")`，`cleanedX=266.3%`、`cleanedPosX=15.1%`，
与 `getCleanedPatchStyle` 的公式一致）。所以问题在**这张图没显示出来**或**显示的区域没被擦干净**。

待查清单（按可能性排序）：

1. **mtlocal 图片有没有真的加载成功**：`bgImg` 是 computed style，无论加载成功与否都会显示 URL。
   需要在自检页里 `new Image()` 加载该 URL 并回报 `naturalWidth` / `onerror`；
   若失败 → 查 `BrowserOverlayImageStore` 的 LRU 是否提前淘汰了 token（`MAX_RENDERED_SCENES` 与
   store 容量是否匹配）。
2. **清理图里那一块到底擦没擦**：把清理图按同样的 `background-size/position` 贴一份到页面上
   做并排对照（`.verify/web/index.html` 已经有 ⑧ 组对照图）。
   若清理图里粉色字还在 → 问题在 `CleanedImageProcessor` 的 mask（粉色字是彩色旁白，
   可能被 `isSolidBubble` 判成 solid 而走了 `includeSolid=false` 时**不擦**的分支）。
3. **遮罩框太小**：粉色旁白框现在被收紧到 `37.55 × 3.21`（高度 45px）。
   若原字的上下缘超出这条带 → 看起来「没擦」。这与第 2 步的 C/D 同源。

**建议先做 1 和 2 的诊断**，再决定改哪儿。诊断脚本写成
`.verify/web/cleanedcheck.html`：加载清理图、按遮罩的 `background-size/position` 贴出来、
逐项 log `naturalWidth` / 目标区域的平均色（和原图同区域对比）。

## 3. 执行顺序与验收

| 顺序 | 事项 | 依赖 | 验收方式 |
|---|---|---|---|
| 1 | 几何来源显式化（第 1 步） | — | 切 PaddleOCR 的 `MTDUMP` 与改动前一致 |
| 2 | 倾角逐行中位数（2.2） | 1 | 单测 + `syn1` 斜排角度靠近 20° |
| 3 | 排版框/字号/位置（2.1 / 2.3 / 2.4） | 1,2 | 单测 + 对照页人眼 |
| 4 | seam 单覆盖框（第 3 步） | — | A/B 两半遮罩框逐字段一致 |
| 5 | 粉字清理图诊断（第 4 步） | — | `cleanedcheck.html` 全绿 |

每一步都要求：

- `node app/src/test/js/mt-overlay-acceptance.test.js` 全绿（当前 123）；
- `.\gradlew :app:testDebugUnitTest :core-translate:testDebugUnitTest :core-overlay:testDebugUnitTest` 全绿；
- `rendercheck.html` 在真实 WebView 全绿（当前 34）；
- 设备上跑一遍 `dump.html`，把 `MTDUMP` 与本计划第 1 节表格对比。

## 4. 风险与取舍

- **不要为了 ML Kit 改 PaddleOCR 的路径**：PaddleOCR 的四边形是准的，任何「收紧/估计」
  都只会让它变差。第 1 步的分支就是为了隔离这一点。
- **倾角估计有物理上限**：ML Kit 不给四边形，我们只能从像素推。对**单个字**或**两三个字**
  的斜排，主轴信噪比低，可能估不出来 —— 这种情况下**宁可不转**（保持轴对齐），
  也不要转错角度（转错比不转更难看）。
- **收紧框会让字号变大**：框变小 → 按框高拟合的字号变小；但原字高拟合会让字号变大。
  2.4 的规则（起点原文、上限框高）就是为了让两者不打架。
- **seam 合并遮罩后，贴片可能出现「遮罩比贴片大」的空档**：需要保证贴片按
  `patch_box` 画在遮罩内时边界对齐，否则会出现一条没贴到图的缝。第 3 步验收要专门看这一条。
